## 逐条分析

### INV-01 截止日期不能早于创建时间

**定义**：`deadline >= createdAt`。如果创建时间是 2026-05-26 10:00，截止日期不能填 2026-05-25。

**覆盖状态：无覆盖**

**现状说明**：
- 没有任何测试构造 `deadline < createdAt` 的 Task 并断言抛出异常
- 没有任何测试试图通过 Service 创建这样的任务
- 代码中不存在对应的校验逻辑（异味分析已指出该不变量完全缺失）

**为什么容易出现**：
当前测试 TP002 和 TP023-TP027 虽然涉及 deadline，但它们构造的 deadline 总是未来时间（如 `2026-06-15`、`2026-07-01`），永远不会触发 INV-01。这些测试只能在"正向"验证 deadline 字段的赋值行为，无法暴露缺失的校验。

---

### INV-02 高优先级任务必须设置截止日期

**定义**：`priority === High` 时，`deadline` 不能为空。

**覆盖状态：无覆盖**

**现状说明**：
- 没有任何测试创建 `priority = HIGH` 且 `deadline = undefined` 的任务并断言异常
- TP001 创建了 HIGH 优先级的任务但**不传** `dueDate`，测试预期是"成功创建"（第 56-74 行），这反而在**反向验证"INV-02 不存在"**——因为这条不变量尚未实现，所以测试通过

```typescript
// TP001 — 当前通过，但本应失败（如果 INV-02 已实现的话）
it('TP001 传入合法参数应创建任务', () => {
  const input: CreateTaskCommand = {
    userId: 'u1',
    title: '学 TypeScript',
    priority: 'HIGH',       // ← HIGH 但无 dueDate
  };
  const task = service.createTask(input);
  // ...断言通过
});
```

**影响**：TP001 当前是一条测试"正向路径"的用例。如果实现 INV-02，TP001 会从"成功创建"变为"抛出异常"，必须同步修改。

### INV-03 标题不能为空

**定义**：标题至少包含一个非空字符（不包括空格）。

**覆盖状态：有覆盖（间接）**

**已存在的测试**：

| 测试 | 位置 | 验证内容 |
|------|------|---------|
| TP003 | TaskService.test.ts:98 | 空字符串 `''` → throw |
| TP005 | TaskService.test.ts:113 | 纯空格 `'   '` → throw |
| task.test.ts:67 | task.test.ts:67 | 空字符串 `'   '` → throw |

**覆盖问题**：
- 三条测试都是通过 `service.createTask()` 间接验证的，不是通过 `new Task(...)` 直接验证
- 如果未来将 INV-03 校验从 Service 层迁移到 Task 构造函数（如重构方案设计所述），现有测试仍会通过（因为 Service 依然会 throw），但不会覆盖"Task 构造函数直接拒绝空标题"这一新行为——如果迁移过程中出错（如忘记迁移校验逻辑），现有测试会因为 Service 把校验委托给了 Task 而继续通过，从而掩盖问题

**覆盖充分性**：边界情况覆盖齐全（空串、纯空格），但测试与实现绑定在同一层次。

---

### INV-04 状态转换必须遵循允许路径

**定义**：PENDING → IN_PROGRESS → COMPLETED → PENDING（不允许跳转）。

**覆盖状态：有覆盖（间接）**

**已存在的测试**（共 8 条）：

| 路径类型 | 测试 | 来源 |
|---------|------|------|
| ✅ PENDING → IN_PROGRESS | TP012 | TaskService.test.ts:184 |
| ✅ IN_PROGRESS → COMPLETED（+ completedAt） | TP008 / task.test 完成时间 | TaskService.test.ts:140 / task.test.ts:26 |
| ✅ COMPLETED → PENDING（+ completedAt 清空） | TP013 | TaskService.test.ts:193 |
| ❌ PENDING → COMPLETED（跳过 IN_PROGRESS） | TP011 / TP015 | TaskService.test.ts:169 / :215 |
| ❌ COMPLETED → IN_PROGRESS | TP016 | TaskService.test.ts:224 |
| ❌ COMPLETED → COMPLETED（重复完成） | TP010 | TaskService.test.ts:161 |
| ❌ IN_PROGRESS → IN_PROGRESS（相同状态） | TP017 | TaskService.test.ts:237 |

**覆盖充分性**：状态转换的覆盖非常完备——全部 3 条合法路径和 4 条非法路径都有测试。TP编号的连续性（TP008-TP017）也说明这是测试设计的重点。

**覆盖问题**：
- 全部通过 `service.completeTask()` / `service.updateTaskStatus()` 间接测试，没有一条通过 `task.updateStatus()` 直接测试
- 与 INV-03 相同的问题：当重构将校验逻辑从 Service 层迁移到 Task 实体时，现有测试无法验证"迁移是否完整"

**覆盖空白**：
- 缺少一条"IN_PROGRESS → PENDING（非法回退）"的测试——当前允许路径只允许 COMPLETED 回退到 PENDING，不允许 IN_PROGRESS 直接回退到 PENDING

### INV-05 提醒时间不能晚于任务截止日期

**定义**：如果 `reminderTime` 和 `deadline` 同时存在，则 `reminderTime <= deadline`。

**覆盖状态：无覆盖**

**现状说明**：
- 没有任何测试涉及 `reminderTime` 与 `deadline` 的先后关系
- 没有任何测试调用 `task.setReminderPolicy()` 并断言异常
- 代码中该不变量仅有一个 TODO 注释（`Task.ts` 第 36 行），校验逻辑完全缺失

**原因分析**：`reminderTime` 是"设置提醒"功能（FR-09）的输入，该功能在需求文档中优先级为"低"，并非当前 5 个核心功能之一。测试也未涉及。

---

### INV-06 完成率始终在 0% 到 100% 之间

**定义**：`completionRate = completed / total * 100`，结果在 [0, 100] 范围内。

**覆盖状态：自然保证（测试反向覆盖）**

**已存在的测试**：

| 测试 | 验证内容 |
|------|---------|
| TP028 | `total: 5, completed: 3` → rate 隐含 60% |
| TP029 | `total: 0, completed: 0` → 边界：空任务 |
| TP030 | `total: 2, completed: 2` → rate 隐含 100% |
| TP031 | `total: 3, completed: 0` → rate 隐含 0% |

**评价**：
- 该不变量由除法运算自然保证，不需要主动校验"超出范围"——只要分子 ≤ 分母，结果就在 [0, 100]
- 现有测试通过 `getUserProgress` 覆盖了 0%、0/0、100%、中间值四种情况，足够充分
- 如果在测试中硬编码验证"rate 在 0-100 之间"属于过度测试
