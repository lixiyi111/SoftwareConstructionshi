# StudyFlow 学习任务管理系统 —— 提示词记录表

> 软件构造课程实验  
> 记录项目实施过程中各阶段使用的 AI 提示词

## 阶段一：需求分析

### 任务说明

生成项目的需求文档，包含用户角色、用户故事、功能需求、非功能需求和验收标准。

### 使用的提示词

```
你现在是软件构造课程实验助手。

请基于以下约束帮我整理软件需求。

1. 功能目标：
我现在要做一个叫 StudyFlow 的学习任务管理系统，主要是给学生个人使用的，不考虑多人协作。

我目前想到的核心功能大概有这些：

- 可以创建学习任务
- 任务需要有标题、描述、优先级这些基本信息
- 可以设置截止时间
- 可以设置任务提醒
- 可以查看所有任务
- 可以修改和删除任务
- 任务应该有状态，比如待开始、进行中、已完成
- 可以按优先级或者状态筛选任务
- 最后还想做一个简单的学习统计，比如完成了多少任务、完成率之类

我希望整个系统偏轻量，不要做成特别复杂的商业项目。

2. 输入输出：

输入：
- 用户输入任务信息
- 用户点击按钮进行创建、修改、删除、筛选等操作

输出：
- 系统展示任务列表
- 显示任务状态和优先级
- 展示简单统计结果
- 到提醒时间时给出提醒

3. 非功能要求：

- 页面操作不要太卡
- 数据刷新后不能丢
- 项目结构尽量清晰
- 后面方便继续扩展
- 界面简单易用即可

4. 不允许做的事情：

- 不要加入聊天、社交、支付、推荐算法这些功能
- 不要做成大型管理系统
- 不考虑管理员、多用户权限
- 不要设计特别复杂的数据库结构
- 不要过度工程化

5. 期望输出格式：

请帮我整理成正式一点的软件需求文档。

输出内容包括：
1. 用户角色
2. 用户故事
3. 功能需求
4. 非功能需求
5. 可测试的验收标准

要求：
- 至少8条功能需求
- 至少4条非功能需求
- 至少5条验收标准
- 验收标准必须是可验证的
- 用 Markdown 格式输出
- 最终整理成 docs/需求文档.md 的内容

项目名称：
StudyFlow 学习任务管理系统
```

### 人工修改记录

AI 生成初稿后，人工检查并做了以下调整：

**修改 1：补充搜索功能需求**
> 需求文档里缺少搜索功能，再加一条 FR-10 按关键词搜索任务，对应的验收标准也补上 AC-07。

**修改 2：调整功能优先级**
> FR-09 提醒设置对 MVP 来说不急，优先级改成"低"，FR-03 优先级设置也属于基础功能，改成"中"。

**修改 3：删除一条冗余的验收标准**
> AC-01 里已经包含了"状态显示为待开始"，原来单独有一条"创建任务后默认状态为待开始"的验收标准删掉，避免重复。

### 生成结果

| 项目 | 内容 |
|------|------|
| 输出文件 | docs/需求文档.md |
| 功能需求 | 10 条（FR-01 ~ FR-10） |
| 非功能需求 | 5 条（NFR-01 ~ NFR-05） |
| 验收标准 | 7 条（AC-01 ~ AC-07） |
| 用户故事 | 8 条（US-01 ~ US-08） |
| 用户角色 | 1 个（学生） |

## 阶段二：领域建模

### 任务说明

基于需求文档进行领域建模，识别核心领域对象，区分实体与值对象，定义不变量。

### 使用的提示词

```
你现在是软件构造课程实验助手。

我已经完成了 StudyFlow 学习任务管理系统 的第一版需求分析，
现在需要继续完成"领域建模"部分。

项目背景：
StudyFlow 是一个面向学生个人使用的学习任务管理系统，
主要功能包括：
- 创建学习任务
- 设置优先级
- 设置提醒
- 更新任务状态
- 查看学习进度统计

这是课程实验项目，
不要设计成大型商业系统，
不要加入复杂微服务、分布式、AI推荐、多人协作等内容。

现在请你帮我完成领域建模分析。

要求：

1. 给出系统中的核心领域对象
至少包括：
- User
- Task
- TaskList
- ReminderPolicy
- ProgressReport

2. 对每个领域对象说明：
- 对象作用
- 主要属性
- 对象之间的关系

3. 标识哪些属于：
- 实体（Entity）
- 值对象（Value Object）

并说明判断原因。

4. 给出对象之间的关系说明，例如：
- 一个 User 可以拥有多个 Task
- 一个 TaskList 包含多个 Task

尽量使用简单清晰的文字表达，
不要写成特别复杂的 UML 理论说明。

5. 给出至少 3 条关键不变量（Invariant）

要求：
- 必须是系统长期需要保持成立的规则
- 要符合学习任务管理系统场景
- 不要写空泛规则

除了下面这些示例外，
请再补充合理的不变量：

示例：
- 任务截止时间不能早于创建时间
- 已完成任务不能再次被修改为未开始状态
- 高优先级任务必须具有截止日期

6. 输出风格要求：
- 用课程实验报告风格编写
- 内容清晰、容易理解
- 不要过度专业化
- 不要写成企业架构文档

7. 最终请直接生成：

docs/领域建模.md

使用 Markdown 格式输出完整文档内容。

8. 不需要生成代码。
只输出领域建模分析文档。
```

### 迭代追加提示

在领域建模文档生成后，补充了类图需求：

```
对于领域建模，需要有对应的类图
```

### 人工修改记录

AI 生成初稿后，人工检查并做了以下调整：

**修改 1：删除冲突的不变量**
> 示例中的"已完成任务不能再次被修改为未开始状态"跟需求 FR-04（已完成可重置为待开始）冲突，这条不变量去掉，换成 INV-06 完成率范围约束。

**修改 2：补充 UML 类图**
> 只有文字描述不够直观，追加指令要求生成 Mermaid 类图，补充对象关系、关联多重性和枚举类型。

**修改 3：统一枚举命名风格**
> 初稿中 TaskStatus 和 Priority 的枚举值混用了英文和中文，统一改成英文大写（PENDING / IN_PROGRESS / COMPLETED），文档中配合中文说明。

### 生成结果

| 项目 | 内容 |
|------|------|
| 输出文件 | docs/领域建模.md |
| 领域对象 | 5 个（User、Task、TaskList、ReminderPolicy、ProgressReport） |
| 实体 | User、Task |
| 值对象 | TaskList、ReminderPolicy、ProgressReport |
| 不变量 | 6 条（INV-01 ~ INV-06） |
| 追加内容 | UML 类图（Mermaid 语法） |

## 阶段三：项目骨架生成

### 任务说明

基于需求文档和领域模型，生成项目目录结构、配置文件、基础脚手架代码。

### 使用的提示词

```
你现在是软件构造课程实验助手。

我已经完成了 StudyFlow 学习任务管理系统 的需求分析和领域建模，
现在需要完成"项目骨架生成"部分。

项目技术栈：
- TypeScript
- Node.js 20+
- Vitest
- ESLint
- Prettier
- Git

这是软件构造课程实验项目，
重点是体现：
- 分层设计
- 模块职责划分
- 工程初始化
- 可维护性

不要设计成大型商业项目，
不要加入：
- Docker
- 微服务
- 数据库
- Redis
- 消息队列
- JWT
- 前后端分离
- 复杂框架

当前阶段只需要"项目骨架"和"基础工程结构"。

请基于以下目录结构生成初始化方案：

src/
  domain/
  application/
  infrastructure/
  interfaces/

test/
docs/

要求：

1. 输出完整项目目录结构

要求：
- 使用树状结构展示
- 每个目录后面简单说明职责
- 不要出现无关目录

2. 生成 package.json

要求：
- 使用 TypeScript + Node.js
- 包含基础 scripts：
  - dev
  - build
  - test
  - lint
  - format
- 使用适合课程实验的最小依赖
- 不要加入复杂工程化工具

3. 生成基础配置建议

包括：
- tsconfig.json
- eslint 配置建议
- prettier 配置建议

不需要写特别复杂的规则，
只要适合课程实验即可。

4. 生成 README.md

README 中至少包括：
- 项目简介
- 技术栈
- 项目结构说明
- 安装方式
- 运行方式
- 测试命令
- 模块职责简介

README 风格要求：
- 像学生课程实验项目
- 简洁清晰
- 不要写成开源商业项目文档

5. 生成基础脚手架代码

要求：
- 只生成最基础的占位代码
- 每层可以给一个简单示例文件
- 不要实现完整业务逻辑
- 不要生成大量代码

例如：
- Task.ts
- TaskService.ts
- TaskRepository.ts
- TaskController.ts

每个文件只需要简单结构即可。

6. 输出风格要求：
- 内容清晰
- 模块职责明确
- 适合软件构造课程实验
- 不要过度复杂化

7. 最终请直接输出：
- 项目目录结构
- package.json
- README.md
- 示例代码文件

并按照真实项目文件格式组织输出。

8. 不要自动扩展功能。
严格按照当前实验阶段生成"初始化工程骨架"。
```

### 人工修改记录

AI 生成初稿后，人工检查并做了以下调整：

**修改 1：入口文件去掉 emoji**
> `src/index.ts` 里 console.log 用了 🚀 emoji，部分终端可能显示乱码，改成纯文本。

**修改 2：lint 脚本加上 test 目录**
> 初稿的 lint 只检查 `src/`，测试文件也需要 lint，补上 `--ext .ts` 参数实际上已覆盖，但明确在 package.json 的 format 脚本里加上了 `test/**/*.ts`。

**修改 3：给 domain 层代码补 JSDoc 注释**
> 枚举和类的文件顶部缺少说明性注释，人工补充了中文 JSDoc，标注每个类和枚举的用途，方便后续阅读。

| application 层 | TaskService.ts |
| infrastructure 层 | TaskRepository.ts（接口 + 内存实现） |
| interfaces 层 | TaskController.ts |
| 入口文件 | src/index.ts |
| 测试文件 | test/task.test.ts（2 个测试用例） |
