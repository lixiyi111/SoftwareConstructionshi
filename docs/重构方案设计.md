# 当前问题概述

## 为什么要重构

`docs/领域建模.md` 定义了系统必须始终遵守的 6 条不变量（INV-01 ~ INV-06），但当前代码的实现状况存在系统性问题：

| 不变量 | 当前状况 | 问题类型 |
|--------|---------|---------|
| INV-01 截止日期 ≥ 创建时间 | ❌ 未实现 | **缺失** |
| INV-02 高优先级必设截止日期 | ❌ 未实现 | **缺失** |
| INV-03 标题不能为空 | ✅ 实现在 `DefaultTaskService` | **层次错误** |
| INV-04 状态转换须遵循允许路径 | ✅ 实现在 `DefaultTaskService` | **层次错误** |
| INV-05 提醒时间 ≤ 截止日期 | ⚠️ 仅留 TODO | **缺失** |
| INV-06 完成率 0%-100% | ✅ 计算自然保证 | 正常，无需变动 |

**核心矛盾**：业务规则（不变量）是领域层的核心职责，但当前 3 条未实现、2 条实现在了应用层。这导致：

1. **领域层贫血**：`Task` 实体只持有数据，不保护自身完整性——违反 DDD 中"实体应始终维持有效状态"的原则
2. **应用层臃肿**：`DefaultTaskService.createTask` 承担了校验和业务规则判断，成为"过长函数"问题的根源
3. **规则可绕过**：如果新加一个 `BatchTaskService` 或 `ImportTaskService`，不变量需要重新实现一遍
4. **测试成本高**：测试不变量必须通过 Service 间接测，需要 mock repository，而不能直接构造 Task 测试

## 重构的边界

本次只解决"不变量归属"问题，即：**将 INV-01 到 INV-05 的校验逻辑从应用层迁移到领域层，并在领域层补全缺失的实现**。

不涉及以下内容（即使它们也在异味报告中被提及）：
- 不抽取通用值解析工具（parsePriority / parseStatus 重复问题）
- 不解耦 Controller 的 console.log
- 不引入 DI 容器
- 不修改 / 不删除任何现有功能

# 方案A

## 内联校验模式（Inline Guard Clauses）

| 维度 | 内容 |
|------|------|
| **设计思路** | 将不变量校验直接以 guard clause 形式写在 `Task` 类的构造函数和变更方法中。这是最直观的重构方式——不引入新的抽象、不增加新文件，只把校验逻辑从"错误的位置"搬到"正确的位置"。 |
| **对应风格** | 防御性编程（Design by Contract 的轻量实践） |
| **改动文件数** | 约 4 个（2 个生产代码 + 2 个测试文件） |

---

### 目标

以最小的代码改动量，将全部 5 条不变量（INV-01 ~ INV-05）的校验收归到 `Task` 实体中，使 `Task` 从"数据容器"变为"自保护的实体"。

### 主要改动

**1. `src/domain/Task.ts` — 构造函数增加校验**

```
// 改动前：构造函数什么都不校验，直接赋值
constructor(
  public readonly taskId: string,
  public userId: string,
  public title: string,           // ← 空字符串也可通过
  ...
  public deadline?: Date,         // ← INV-01/02 无校验
  ...
) {}

// 改动后：构造函数开头插入 guard clause，校验通过才继续赋值
constructor(
  public readonly taskId: string,
  public userId: string,
  private _title: string,         // ← 改为 private set，通过 getter 暴露
  ...
  public deadline?: Date,
  ...
) {
  // INV-03: 标题不能为空
  if (!_title || _title.trim().length === 0) {
    throw new Error('任务标题不能为空');
  }
  // INV-01: 截止日期不能早于创建时间
  if (deadline && deadline < createdAt) {
    throw new Error('截止日期不能早于创建时间');
  }
  // INV-02: 高优先级必须设截止日期
  //（注：此时 priority 已经赋值，但 guard clause 在赋值之后执行校验）
  // 可通过调整参数顺序或在校验前先赋值 priority 再检查
}
```

**2. `src/domain/Task.ts` — `updateStatus` 增加状态转换校验**

```
// 改动前：只管理 completedAt，不验证转换路径
updateStatus(newStatus: TaskStatus): void {
  this.status = newStatus;
  if (newStatus === TaskStatus.Completed) {
    this.completedAt = new Date();
  } else {
    this.completedAt = undefined;
  }
}

// 改动后：先校验转换合法性，再变更状态
updateStatus(newStatus: TaskStatus): void {
  this.validateTransition(this.status, newStatus);  // ← 新增
  this.status = newStatus;
  if (newStatus === TaskStatus.Completed) {
    this.completedAt = new Date();
  } else {
    this.completedAt = undefined;
  }
}

// INV-04: 状态转换规则表（从 Service 移入，类型安全）
private validateTransition(current: TaskStatus, next: TaskStatus): void {
  const allowed: Record<TaskStatus, TaskStatus[]> = {
    [TaskStatus.Pending]: [TaskStatus.InProgress],
    [TaskStatus.InProgress]: [TaskStatus.Completed],
    [TaskStatus.Completed]: [TaskStatus.Pending],
  };
  if (!allowed[current]?.includes(next)) {
    throw new Error(`不允许的状态转换: ${current} → ${next}`);
  }
}
```

**3. `src/domain/Task.ts` — `setReminderPolicy` 补全 INV-05**

```
// 改动前：仅 TODO 注释
setReminderPolicy(reminderTime: Date): void {
  // TODO: 校验提醒时间不晚于截止日期（参考 INV-05）
  this.reminderPolicy = new ReminderPolicy(reminderTime);
}

// 改动后：实现 INV-05 校验
setReminderPolicy(reminderTime: Date): void {
  if (this.deadline && reminderTime > this.deadline) {
    throw new Error('提醒时间不能晚于截止日期');
  }
  this.reminderPolicy = new ReminderPolicy(reminderTime);
}
```

**4. `src/application/DefaultTaskService.ts` — 移除重复校验**

```
// 改动前：
createTask(input: CreateTaskCommand): Task {
  if (!input.title || input.title.trim().length === 0) { ... }  // ← INV-03
  const priority = this.parsePriority(input.priority);
  ...
}

// 改动后：createTask 不再校验标题（由 Task 构造函数负责）
createTask(input: CreateTaskCommand): Task {
  const priority = this.parsePriority(input.priority);
  // Task 构造函数自己负责 INV-01/02/03
  const task = new Task(..., input.title.trim(), ...);
  this.repository.save(task);
  return task;
}
```

```
// 改动前：DefaultTaskService 有私有方法 validateStatusTransition
// 改动后：删除该方法，updateTaskStatus 不再调用

// 改动前：
updateTaskStatus(taskId: string, status: string): Task {
  ...
  this.validateStatusTransition(task.status, newStatus);  // ← 移到 Task 内部
  task.updateStatus(newStatus);
  ...
}
```

---

### 优点

1. **改动量极小**：只修改 2 个生产代码文件（`Task.ts` 和 `DefaultTaskService.ts`），不新增文件、不引入新依赖
2. **概念直观**：guard clause 是 TypeScript/Java 开发者最熟悉的防御性编程手法，无需学习新设计模式
3. **渐进式**：可以为每条不变量独立添加校验，分多次 commit 提交，每次改动风险极小
4. **与原架构兼容**：不改变任何接口签名，所有现有测试只需调整断言位置，不需要重写
5. **当前规模最匹配**：项目只有 10 个源文件，引入额外的抽象层反而增加认知负担

### 缺点

1. **构造函数变长**：`Task` 构造函数将从纯赋值变为含 3 条 guard clause 的校验逻辑，行数增加约 20 行
2. **校验逻辑不可复用**：如果有其他地方需要"判断一个 deadline 是否有效"（如 UI 端的前置校验），需要重新写一遍同样的逻辑
3. **测试对象粒度粗**：一条测试用例可能需要构造一个完整的有效 Task 才能测试某一条不变量，setup 代码略多
4. **不变量和实体紧耦合**：如果 INV-02 的规则变化（如"高优先级必须设截止日期"改为"高优先级可选设截止日期"），需要修改 Task 实体的构造函数

### 对现有功能影响

| 功能 | 影响 |
|------|------|
| 创建任务 | `DefaultTaskService.createTask` 行为不变，但标题校验的 throw 位置从 Service 变为 Task 构造函数（调用方感知不到变化） |
| 更新状态 | `DefaultTaskService.updateTaskStatus` 行为不变，状态转换校验从 Service 的私有方法变为 Task 的私有方法 |
| 设置提醒 | `Task.setReminderPolicy` 行为从"无校验"变为"校验提醒时间"，对原有调用方是行为变更（原来能通过的现在可能 throw） |
| 其余功能 | 完全不受影响 |

### 测试迁移成本

| 现有测试 | 迁移方式 |
|---------|---------|
| `TaskService.test.ts` TP003（标题为空） | 测试目标从 `service.createTask()` 改为 `new Task(...)` 构造函数，断言不变 |
| `TaskService.test.ts` TP010/TP011/TP012-017（状态转换） | 测试目标从 `service.updateTaskStatus()` 改为 `task.updateStatus()`，断言不变 |
| `TaskService.test.ts` 其他测试（创建、列表、统计） | 影响极小，Service 行为不变 |
| 新增测试（INV-01、INV-02、INV-05） | 需要新建 `Task.test.ts` 或扩展现有的 `task.test.ts`，覆盖 3 条新不变量 |
| Controller 测试 | 无需变动 |

**综合评估**：约 50%-60% 的现有 Service 测试可以原位保留（只改断言目标），约 30% 需要迁移到新的领域层测试文件，约 20% 需要新增。

# 方案B

## 规格模式（Specification Pattern）

| 维度 | 内容 |
|------|------|
| **设计思路** | 将每条不变量封装为独立的规格（Specification）对象。`Task` 实体通过组合/委托规格来完成自我校验，规格之间彼此独立、可单独测试、可复用。 |
| **对应风格** | 策略模式（Strategy） / 规格模式（Specification） |
| **改动文件数** | 约 8 个（4 个新文件 + 4 个修改文件） |

---

### 目标

建立一套可组合、可独立测试的不变量规格体系，使不变量校验与 `Task` 实体本身的逻辑解耦，并为未来增加新校验规则提供标准化扩展点。

### 主要改动

**1. 新增 `src/domain/specs/Invariant.ts` — 定义规格接口**

创建一个用于描述"一条业务规则"的接口：

```
// 规格接口：一条不变量就是一个规格
interface Invariant<T> {
  // 检查 target 是否满足规则，不满足则 throw
  check(target: T): void;
  // 描述该规则，用于错误信息
  readonly description: string;
}
```

这个接口是整个方案的核心抽象。`T` 可以是 `Task`、也可以是 `ReminderPolicy` 或其他领域对象。

**2. 新增 `src/domain/specs/` 目录 — 每条不变量独立一个文件**

目录结构如下：

```
src/domain/
├── Task.ts
├── specs/
│   ├── Invariant.ts          ← 接口定义（约 8 行）
│   ├── titleNotEmpty.ts      ← INV-03（约 12 行）
│   ├── deadlineNotBeforeCreation.ts  ← INV-01（约 15 行）
│   ├── highPriorityRequiresDeadline.ts  ← INV-02（约 15 行）
│   ├── validStatusTransition.ts  ← INV-04（约 20 行）
│   └── reminderBeforeDeadline.ts  ← INV-05（约 12 行）
```

每个规格文件实现 `Invariant<Task>` 接口。例如 `titleNotEmpty.ts`：

```
export class TitleNotEmpty implements Invariant<Task> {
  readonly description = '任务标题不能为空';

  check(task: Task): void {
    if (!task.title || task.title.trim().length === 0) {
      throw new Error(this.description);
    }
  }
}
```

`validStatusTransition.ts` 接受两个参数（当前状态、目标状态），实现为一个带参数的规格：

```
export class ValidStatusTransition {
  readonly description = '不允许的状态转换';

  check(current: TaskStatus, next: TaskStatus): void {
    // 状态转换映射表
  }
}
```

**3. 新增 `src/domain/TaskValidator.ts` — 组合规格的应用入口**

定义一个 `TaskValidator` 类，封装所有与 `Task` 生命周期相关的规格组合：

```
class TaskValidator {
  // 构造时需校验的规格集
  static forCreation(): Invariant<Task>[] { ... }
  // 更新状态时需校验的规格集
  static forStatusUpdate(): Invariant<...>[] { ... }
  // 设置提醒时需校验的规格集
  static forReminder(): Invariant<...>[] { ... }
}
```

**4. 修改 `src/domain/Task.ts` — 实体通过 Validator 校验自身**

```
// 构造函数中调用校验
constructor(...) {
  TaskValidator.forCreation().forEach(spec => spec.check(this));
  ...
}

updateStatus(newStatus: TaskStatus): void {
  TaskValidator.forStatusUpdate().forEach(spec => spec.check({ current: this.status, next: newStatus }));
  ...
}
```

另一种变体（更轻量）是将规格直接声明为 `Task` 的静态字段，不额外引入 `TaskValidator`：

```
class Task {
  private static readonly creationInvariants: Invariant<Task>[] = [
    new TitleNotEmpty(),
    new DeadlineNotBeforeCreation(),
    new HighPriorityRequiresDeadline(),
  ];

  constructor(...) {
    Task.creationInvariants.forEach(spec => spec.check(this));
  }
}
```

**5. 修改 `src/application/DefaultTaskService.ts` — 简化**

与方案A相同，移除重复校验逻辑。Service 不再关心"哪些规则需要校验"，因为在 Task 构造时已经自动完成。

---

### 优点

1. **单条规则可独立测试**：`TitleNotEmpty.check()` 可以用 3 行测试覆盖，无需构造完整的 Task 对象——只需要 mock 一个满足 `{ title: string }` 接口的对象
2. **规则可复用**：如果 UI 层想做"用户输入时实时校验"，可以直接复用 `TitleNotEmpty` 规格，不需要重新实现
3. **新增规则标准化**：团队新增业务规则时，只需"新建一个规格文件 + 实现 Invariant 接口 + 注册到 TaskValidator"。不需要修改现有类的逻辑，符合开闭原则
4. **不变量变更影响范围小**：如果 INV-02 改为"高优先级可选设截止日期"，只需修改 `highPriorityRequiresDeadline.ts` 一个文件
5. **文档即代码**：`src/domain/specs/` 目录本身就是一份可执行的领域规则目录

### 缺点

1. **文件数量膨胀**：增加约 6-8 个新文件，对于当前只有 10 个源文件的项目来说，重构部分占新增量的 60%-80%
2. **抽象成本过高**：当前项目规模下，Invariant 接口 + 每个规则独立文件 → 对单条只有 5-10 行校验逻辑的规则来说，文件结构开销（import/export/class 定义）可能超过校验逻辑本身
3. **学习成本**：需要团队成员理解"Specification Pattern"的设计意图——对于课程实验场景，这可能偏离了"软件构造"的核心教学目标
4. **过度设计的风险**：如果项目后续不再扩展（保持单用户、CLI 原型），这套规格体系将长期处于"杀鸡用牛刀"的状态
5. **测试文件翻倍**：每个规格文件至少需要配套一个测试文件，测试文件数从 2 个增长到约 8 个

### 对现有功能影响

与方案A完全相同：

| 功能 | 影响 |
|------|------|
| 创建任务 | 行为不变，标题校验 throw 位置变更为 Task 构造函数 |
| 更新状态 | 行为不变，校验逻辑从 Service 迁移到规格对象 |
| 设置提醒 | 行为变更——原来可以设任意时间的提醒，现在会校验 INV-05 |
| 其余功能 | 完全不受影响 |

### 测试迁移成本

与方案A相比，方案B的测试结构变化更大：

| 测试类型 | 迁移方式 |
|---------|---------|
| 现有 Service 测试 | 同方案A，约 30% 需迁移到领域层测试 |
| 规格单元测试（新增） | 每个规格文件需要 3-5 条独立测试，预计新增 20-30 条测试 |
| Task 实体测试（修改） | Task 的构造/更新测试变为"验证校验是否委托给正确的规格" |
| 集成测试 | 保持不变 |

**综合评估**：测试文件数将从 2 个增加到约 8 个，测试总条数从 32 条增加到约 55-65 条。测试覆盖更精细，但维护成本同步上升。

# 方案比较

## 对比总览

| 对比维度 | 方案A 内联校验 | 方案B 规格模式 |
|---------|--------------|--------------|
| **开发成本** | 低（约 2-3 小时） | 中高（约 4-6 小时） |
| **新增文件数** | 0 个 | 6-8 个 |
| **修改文件数** | 2 个生产代码 + 2 个测试 | 2 个生产代码 + 6-8 个测试 |
| **可维护性（当下）** | ★★★★ 好 | ★★★ 中等（文件多） |
| **可维护性（扩展后）** | ★★★ 中等（构造函数膨胀） | ★★★★★ 优秀（开闭原则） |
| **可扩展性** | ★★★ 中——新增规则需修改 Task.ts | ★★★★★ 高——新增规则 = 新增文件 |
| **可测试性** | ★★★★ 好——测试 Task 即可 | ★★★★★ 最佳——每个规格独立测试 |
| **当前项目规模适配度** | ★★★★★ 极高 | ★★ 低（过度设计风险） |
| **团队理解成本** | 极低 | 中（需理解 Specification Pattern） |
| **对原有测试的冲击** | 小（约 30% 迁移） | 大（约 60% 重构） |
| **后续切换成本** | 可后续升级到方案B | 回退到方案A有沉没成本 |

## 关键维度展开

### 开发成本

- **方案A**：只需在一个文件（`Task.ts`）内增加 guard clause + 从 `DefaultTaskService.ts` 删除重复逻辑。测试迁移也机械——把"通过 service 调用"改成"直接构造 Task 调用"。总计约 2-3 小时的编码和测试调整。
- **方案B**：需要先设计 Invariant 接口、再逐个实现 5 个规格文件、再写 TaskValidator 组合、再调整 Task 构造函数、再写对应的规格测试。总计约 4-6 小时。

### 可维护性

- **当下看，方案A 更优**：项目只有 10 个文件、约 400 行代码。引入 6-8 个新文件意味着重构部分使代码库体积膨胀近一倍。方案A 的"所有校验在 Task 内"反而更容易定位和维护。
- **长期看，方案B 更优**：若项目扩展到 50+ 个领域对象、数十条不变量，方案B 的规格目录可以成为"领域规则的目录"，而方案A 的 Task 构造函数将膨胀到无法阅读。

### 可扩展性

- 方案B 明确胜出。开闭原则的收益就在这里：新增"INV-07 子任务总数不超过 10 个"，方案B 只需新建 `src/domain/specs/subtaskLimit.ts`，方案A 需要修改 `Task.ts` 的构造函数或变更方法。

### 当前项目规模适配度

- 方案A 大幅胜出。对于一个实验课程项目，10 个源文件、400 行代码的规模下，引入设计模式的抽象层带来的收益远不能抵消认知成本和文件膨胀成本。

### 测试迁移成本

- 方案A 优势明显。方案B 要求粒度更细的测试（每个规格单独测），虽然覆盖更完整，但对于课程实验来说，测试的投入产出比在方案B 中开始出现边际递减。

---

# 最终建议

## 选择方案A（内联校验模式）

### 作为实验三切入点的理由

**1. 与异构分析形成闭环**

代码异味报告明确指出的第一优先级问题是"领域不变量散落在各层，Task 实体贫血"。方案A 精确地只解决这一个问题——不引入新抽象、不扩散重构范围。评审人可以清晰地看到"异味分析 → 方案设计 → 代码修改"的完整可追溯链路。

**2. 重构价值可验证**

方案A 完成后，以下效果可以直接用测试验证：
- `new Task(...)` 传入空标题 → 立即 throw（INV-03）
- `new Task(...)` 传入早于创建时间的 deadline → 立即 throw（INV-01）
- `task.updateStatus(COMPLETED)` 从 PENDING 直接跳转 → throw（INV-04）

每条不变量对应一条测试、一个 throw、一个明确的改动点。这种"改动-验证"的直接性是实验教学中最容易评估的。

**3. 复杂度受控，适合课程实验**

实验三的目标不是"让学生写出最优雅的架构"，而是"让学生理解重构的决策过程"。方案A 允许学生聚焦在：
- 如何判断一段代码放错了位置（应用层 vs 领域层）
- 如何安全地将逻辑从一处迁移到另一处（不改接口、不改行为）
- 如何通过测试验证迁移的正确性

这些是软件构造课程的核心能力，不需要 Specification Pattern 这样的高阶抽象来支撑。

**4. 未来可升级**

方案A 是方案B 的"前驱步骤"——如果项目规模增长，方案A 中的 `Task.ts` 校验逻辑可以后期以"提取规格"的方式自然演化为方案B。在实验三阶段选择方案A 不会产生沉没成本。

### 预期成果拓扑

```
改动前                          改动后
─────────                      ─────────
DefaultTaskService              DefaultTaskService
  ├── 校验标题 (INV-03)           ├── → 删除此逻辑
  ├── 状态转换校验 (INV-04)        ├── → 删除此逻辑
  ├── 创建任务                     └── 创建任务（简化为纯编排）
  └── 更新状态
                                  Task（自保护实体）
Task（数据容器）                     ├── 构造时校验 INV-01/02/03
  ├── 属性字段                      ├── updateStatus 校验 INV-04
  ├── updateStatus                  └── setReminderPolicy 校验 INV-05
  └── setReminderPolicy（TODO）
```

### 不选择方案B的理由

方案B 是一个"正确的设计"，但它更适合以下场景：
- **项目持续演进 3 个以上版本**，有明确的新规则接入预期
- **团队有 3 人以上协作**，需要显式的规则契约来避免冲突
- **领域规则超过 15 条**，内联校验会导致实体类过于臃肿

当前 StudyFlow 项目不满足上述任一条件。在实验课程中过早引入设计模式，反而会使重构方案"为模式而模式"，偏离了"解决实际问题"的重构本意。

## 实施路线建议

无论选择哪个方案，建议按以下顺序逐步实施（每条不变量独立交一次 commit）：

```
Step 1: INV-03 标题非空（最简单，已有实现可参考）
        └── 将校验逻辑从 Service 迁移到 Task 构造函数
        └── 更新测试

Step 2: INV-04 状态转换（已有实现，纯搬运）
        └── 将 validateStatusTransition 从 Service 迁到 Task
        └── 更新测试

Step 3: INV-01 截止日期 ≥ 创建时间（全新实现）
        └── Task 构造函数增加 guard clause
        └── 新增测试

Step 4: INV-02 高优先级必须设截止日期（全新实现）
        └── Task 构造函数增加 guard clause
        └── 新增测试

Step 5: INV-05 提醒时间 ≤ 截止日期（实现 TODO）
        └── setReminderPolicy 补全校验
        └── 新增测试

Step 6: 清理 Service 层
        └── 确认 Service 中不再包含任何不变量校验
        └── 确认现有集成测试全部通过
```

这种分步方式确保每一步的改动范围最小、可独立验证，且任何一步出问题都可以快速定位。
