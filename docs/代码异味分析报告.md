# StudyFlow 项目代码异味分析报告

> 分析日期：2026-06-07
> 分析范围：`src/` 目录下全部源代码（10 个文件）
> 项目架构：四层架构（domain — application — infrastructure — interfaces）

---

# 设计假设

本分析基于以下假设进行：

1. **四层架构意图**：项目按 domain → application → infrastructure → interfaces 四层组织，符合 DDD 分层思想。分析以此分层意图为基准，判断各层职责是否得到正确落实。

2. **目标用户为单学生**：需求文档明确系统只有"学生"一个角色，暂不考虑多用户权限、团队协作等扩展。分析中的可扩展性评估基于"在未来可能引入更多用户角色或任务类型"这一合理预期。

3. **当前为 CLI 原型阶段**：目前 interface 层通过 `console.log` 输出，尚未接入 Web 框架或 GUI。分析将其视为早期原型，判断当前架构能否平滑过渡到真实 UI。

4. **领域不变量有明确文档**：`docs/领域建模.md` 定义了 INV-01 至 INV-06 共 6 条不变量。分析以这些不变量是否在代码中得到落实作为领域层完整性的判断依据。

5. **分析只诊断不治疗**：本报告只定位问题、评估影响和优先级，不提供重构实现方案。

## 过长函数

### 问题一：`DefaultTaskService.createTask` 身兼多责

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts) 第 24-44 行

**问题描述**：
`createTask` 方法在约 20 行内完成了四项不同职责：参数校验（标题非空）、值解析（字符串→枚举）、对象构建（new Task）、持久化（repository.save）。虽然绝对行数不算多，但四个步骤属于不同的抽象层次——校验和解析属于输入处理，对象构建属于领域工厂，持久化属于基础设施——全部揉在一个方法中，违反了"单一抽象层次原则"（SLAP）。

**影响**：
- 新增校验规则（如 INV-02：高优先级必须设截止日期）时，必须修改 `createTask` 方法体，方法会持续膨胀
- 无法独立测试"校验"、"解析"、"构建"、"持久化"中的任意一个环节
- 后续若引入批量创建任务功能，这部分逻辑无法直接复用

**严重程度**：中

---

### 问题二：`TaskController` 中各处理方法混合业务编排与展示

**文件**：[src/interfaces/TaskController.ts](src/interfaces/TaskController.ts) 第 11-62 行

**问题描述**：
Controller 中 6 个方法的共同模式是"调用 service → 判断结果 → console.log 输出"。以 `handleListByPriority`（第 29-39 行）和 `handleListDueTasks`（第 42-52 行）为代表，每个方法都内联了"空结果检查 + 循环格式化输出"的逻辑。这些方法虽然不是行数意义上的"长"，但将"判断-格式化-输出"三重逻辑直接写在同一个方法中，使得切换到 Web 响应（返回 JSON）或 GUI 渲染时必须重写整个方法。

**影响**：
- 展示逻辑与接口逻辑耦合，无法替换输出目标（CLI → HTTP → GUI 需重写）
- 格式化逻辑（如 `[${t.priority}] ${t.title}（${t.status}）`）散落在各个方法中，无法统一维护
- 测试时需要捕获 `console.log` 输出，增加测试复杂度

**严重程度**：中

## 重复代码

### 问题一：`parsePriority` 与 `parseStatus` 结构完全一致

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts) 第 98-118 行

**问题描述**：
两个私有方法采用了完全相同的实现模式：

```
建立 Record 映射表 → 查表 → 未命中则 throw Error
```

```typescript
// parsePriority (第 98-107 行)
private parsePriority(value: string): Priority {
  const map: Record<string, Priority> = { HIGH: ..., MEDIUM: ..., LOW: ... };
  const p = map[value.toUpperCase()];
  if (!p) throw new Error(...);
  return p;
}

// parseStatus (第 109-118 行) — 完全相同的结构
private parseStatus(value: string): TaskStatus {
  const map: Record<string, TaskStatus> = { PENDING: ..., IN_PROGRESS: ..., COMPLETED: ... };
  const s = map[value.toUpperCase()];
  if (!s) throw new Error(...);
  return s;
}
```

唯一差异是枚举类型和错误信息模板不同。"字符串→枚举"的解析逻辑本质上是同一个概念，被复制了两份。

**影响**：
- 每新增一种枚举解析（如后面可能加 `SortBy`、`Category` 等），就要再复制一遍相同结构
- 若想改变解析行为（如忽略大小写方式变化、增加日志、支持别名），需要修改所有复制点

**严重程度**：高

---

### 问题二：`findAll()` + 内存过滤模式重复三次

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts)

**问题描述**：
`listTasksByPriority`（第 70-74 行）、`listDueTasks`（第 78-83 行）、`getUserProgress`（第 87-94 行）三个方法都重复同一模式：

```
const all = this.repository.findAll();   // 加载全部数据
// 然后在内存中过滤/排序
```

在数据量少时这不是性能问题，但三个方法各自独立地编写了这一模式，没有提取公共查询逻辑。

**影响**：
- 将来若更换为数据库实现，每个方法都需要改为 SQL/查询语句，修改点分散
- `TaskRepository` 接口未提供按条件查询能力（如 `findByUserId`、`findByDeadlineBefore`），导致过滤职责上浮到应用层
- 测试时需要关注每个方法是否都正确处理了空结果情况

**严重程度**：中

### 问题三：Controller 中空结果检查模式重复

**文件**：[src/interfaces/TaskController.ts](src/interfaces/TaskController.ts)

**问题描述**：
`handleListByPriority`（第 31-34 行）和 `handleListDueTasks`（第 43-46 行）都包含以下模式：

```typescript
if (tasks.length === 0) {
  console.log('[INFO] ...');
```

两句的差异仅仅是提示文案不同。类似的"空→提示→提前返回"逻辑是重复的防御性编程痕迹。

**影响**：
- 如果统一调整空结果提示风格（如加 emoji、改为 throw），需要改两处
- 新增列表类操作时容易复制这一模式

**严重程度**：低

## 条件分支过多

### 问题一：状态转换验证逻辑用二维映射表达复杂规则

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts) 第 120-130 行

**问题描述**：
`validateStatusTransition` 使用 `Record<string, string[]>` 来编码状态转换规则。当前只有 3 个状态、3 条允许路径，复杂度尚可接受。但映射表的结构存在隐性问题：

- 使用字符串类型作为键和值，丢失了编译期类型检查（虽然当前输入已经过 `parseStatus` 转换，但函数签名本身就是 `(current: TaskStatus, next: TaskStatus)`，却又在内部转成了字符串索引）
- 若任务状态增加到 5 个（如增加"已取消"、"已归档"），允许路径的组合数会从 3 条膨胀到约 10-15 条，映射表将变得难以维护

**影响**：
- 状态转换规则和业务逻辑耦合在应用层中，而不是由领域实体（Task）自己控制
- 新增状态时需要同时修改映射表和所有涉及状态判断的逻辑
- 对非法的状态-状态组合缺乏编译期保障

**严重程度**：中

---

### 问题二：`Task.updateStatus` 中隐含时间分支

**文件**：[src/domain/Task.ts](src/domain/Task.ts) 第 25-32 行

**问题描述**：
`updateStatus` 包含了一个 if-else 分支来管理 `completedAt`：
```
if (newStatus === Completed) → 设置 completedAt = new Date()
else → 清空 completedAt = undefined
```

这个分支逻辑有两个问题：
1. `new Date()` 直接调用导致不可测——测试中无法控制"完成时间"
2. 分支虽简单，但把"状态变更"和"时间记录"两个关注点耦合在一起。未来如果要记录"开始时间"（进入 IN_PROGRESS 时）或"暂停时间"，分支会变得更复杂

**影响**：
- 测试中含有时间断言时（如 `expect(task.completedAt).toBeInstanceOf(Date)`），无法验证具体时间值
- 扩展时间记录行为时必须修改此方法

**严重程度**：低

## 模块职责混乱

### 问题一：领域不变量散落在各个层次，部分未实现

**文件**：涉及多文件

**问题描述**：
`docs/领域建模.md` 定义了 6 条不变量（INV-01 ~ INV-06），但在代码中的落实情况如下：

| 不变量 | 实现状态 | 实现位置 | 问题 |
|--------|---------|---------|------|
| INV-01 截止日期 ≥ 创建时间 | ❌ 未实现 | — | 完全没有校验 |
| INV-02 高优先级必须设截止日期 | ❌ 未实现 | — | `createTask` 未检查 |
| INV-03 标题不能为空 | ✅ 已实现 | `DefaultTaskService.createTask` | 但属于应用层，不应由它负责 |
| INV-04 状态转换路径 | ✅ 已实现 | `DefaultTaskService.validateStatusTransition` | 属于应用层而非领域层 |
| INV-05 提醒时间 ≤ 截止日期 | ⚠️ 仅留 TODO | `Task.setReminderPolicy` | TODO 注释，未实现 |
| INV-06 完成率 0%-100% | ✅ 已实现 | `TaskController.handleShowProgress` | 计算本身自然保证 |

INV-03 和 INV-04 虽然实现了，但放在应用层而不是领域层。如果未来换一个 Service 实现（如 `AdvancedTaskService`），这些核心业务规则需要重新实现。INV-01、INV-02、INV-05 则完全缺失。

**影响**：
- 核心业务规则分散且不完整，存在数据不一致风险
- 领域层（`Task` 实体）未充分履行"保护不变量"的职责
- 违反了 DDD 中"领域层应该是业务规则的核心，不依赖外部层次"的原则

**严重程度**：高

### 问题二：`DefaultTaskService` 承担过多协调职责

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts)

**问题描述**：
`DefaultTaskService` 同时承担了以下职责，导致类内聚度偏低：

1. **输入校验**：标题非空检查
2. **值解析**：字符串→枚举转换（parsePriority、parseStatus）
3. **业务规则**：状态转换合法性校验
4. **对象编排**：调用 repository 进行持久化
5. **查询逻辑**：在内存中过滤、排序、统计

根据单一职责原则，"应用服务"的职责应该是"编排领域对象完成一个用例"，而不是自己完成所有计算和转换。当前代码中，值解析（2）和查询逻辑（5）更应属于领域层或基础设施层。

**影响**：
- 领域层（`Task` 实体）变成了"贫血模型"——只持有数据，不含业务逻辑
- 测试时需要 mock repository，即使只是想测试简单的值解析逻辑
- 业务逻辑无法在其他应用服务中复用

**严重程度**：高

### 问题三：`TaskController` 中的展示逻辑与接口逻辑耦合

**文件**：[src/interfaces/TaskController.ts](src/interfaces/TaskController.ts)

**问题描述**：
Controller 的所有方法都直接调用 `console.log` 进行输出。这意味着：
- 输出格式（缩进、标签符号、emoji）与接口处理逻辑在同一方法中
- 若要改为 API 返回 JSON，需要完全重写 Controller
- 多个方法包含重复的格式字符串（如 `[${t.priority}] ${t.title}（${t.status}）`）

Controller 的职责应该是"接收请求 → 调用应用层 → 返回响应"。当前实现把"格式化响应"的职责也塞进来了。

**影响**：
- 无法在不修改 Controller 的情况下更换展示层（CLI ↔ HTTP ↔ GUI）
- 格式化字符串散落在各个方法中，无法统一维护
- 测试时必须捕获 stdout，测试代码包含大量 `console.log` 断言

**严重程度**：中

## 难以测试的耦合点

### 问题一：硬编码 `randomUUID()` 导致 ID 不可控

**文件**：[src/application/DefaultTaskService.ts](src/application/DefaultTaskService.ts) 第 31 行

**问题描述**：
```typescript
const task = new Task(
  randomUUID(),  // ← 每次调用生成随机 ID，不可预测
  ...
);
```

`randomUUID()` 直接硬编码在 `createTask` 方法中，无法从外部注入 ID 生成策略。测试中若需要断言某个 `taskId`，只能通过 `task.taskId` 读取而非事先已知，也无法验证两个引用是否指向同一个 task。

**影响**：
- 测试中无法使用确定性的 taskId，所有断言都必须"读回来再比"
- 若将来需要业务自定义 ID 格式（如 `TASK-2026-0001`），需要修改 `createTask` 方法体
- 无法在不运行完整方法的前提下验证 ID 生成逻辑

**严重程度**：中

### 问题二：`Task.updateStatus` 内部 `new Date()` 导致时间不可控

**文件**：[src/domain/Task.ts](src/domain/Task.ts) 第 27 行

**问题描述**：
```typescript
updateStatus(newStatus: TaskStatus): void {
  this.status = newStatus;
  if (newStatus === TaskStatus.Completed) {
    this.completedAt = new Date();  // ← 系统时间，无法注入
  } else {
    this.completedAt = undefined;
  }
}
```

`completedAt` 的值取决于方法执行的系统时间，测试中只能断言"这是一个 Date 对象"，无法验证具体的时间值。若测试在跨日边界执行，甚至可能出现日期不一致的假阳性。

**影响**：
- 测试无法验证时间准确性（如"完成时间应在操作后 1 秒内"）
- 测试依赖于系统时钟，存在不稳定性
- 时间策略（如使用 UTC 还是本地时间、精度到毫秒还是秒）不可配置

**严重程度**：中

### 问题三：`TaskController` 依赖 `console.log` 导致接口层不可测试

**文件**：[src/interfaces/TaskController.ts](src/interfaces/TaskController.ts)

**问题描述**：
Controller 的 6 个方法全部依赖 `console.log` 输出结果。目前测试（`test/application/TaskService.test.ts`）直接跳过了 Controller 层测试，仅覆盖了 Service 层。如果要写 Controller 测试，必须：

1. mock `console.log`（或 `console` 的全局对象）
2. 恢复原始 `console.log` 以避免测试间污染
3. 通过捕获的输出来断言行为

这种测试方式脆弱且繁琐，而且本质上是在测试"字符串格式"而非"接口行为"。

**影响**：
- Controller 层的测试成本高，导致实际没有 Controller 测试
- 当前的测试覆盖率在高分层（Controller）上有严重缺口
- 若切换到 HTTP 框架（如 Express），现有 Controller 代码全部需要重写，测试也全部需重写

**严重程度**：高

### 问题四：`InMemoryTaskRepository` 使用共享可变状态

**文件**：[src/infrastructure/TaskRepository.ts](src/infrastructure/TaskRepository.ts) 第 19 行

**问题描述**：
`InMemoryTaskRepository` 内部使用一个 `Map<string, Task>` 实例字段来存储所有任务。该实例在测试中通过 `createFixture()` 每次创建新实例的方式隔离，但：

1. 如果测试代码意外使用了全局/模块级 repository 实例（如 `src/index.ts` 第 12 行定义了一个全局 repository），测试可能受到干扰
2. `findAll()` 返回的是 `Array.from(this.tasks.values())`——返回的是 Task 对象引用而非快照，外部修改 Task 会直接改变仓储内的状态
3. 无事务支持，并发操作（即使目前是单线程）可能导致数据不一致

**影响**：
- 测试间可能因共享引用而产生隐式依赖
- 定位测试失败原因时需要考虑"数据是否被之前的测试污染"
- 无法直接替换为持久化仓储来验证"真实"场景

**严重程度**：中

### 问题五：缺少依赖注入容器，测试时只能手动装配

**文件**：[src/index.ts](src/index.ts) 第 12-14 行

**问题描述**：
```typescript
const repository = new InMemoryTaskRepository();
const taskService = new DefaultTaskService(repository);
const ctrl = new TaskController(taskService);
```

当前采用手动依赖注入（构造函数注入），这在小型项目中行得通。但测试代码（`test/application/TaskService.test.ts`）中也需要重复相同的组装逻辑，且每次只能替换整个 Repository 而非单个方法。

**影响**：
- 如果要 mock `repository.findById` 来测试"任务不存在"场景，当前无法做到（因为 `InMemoryTaskRepository` 是具体类而非通过接口配置）
- 测试辅助函数 `createFixture()` 在各 describe 块中重复定义
- 组装逻辑散落在生产代码和测试代码中，修改依赖关系时需要更新多处

**严重程度**：低

# 重构优先级建议

## 第一优先级（实验三切入）

### 领域不变量集中到领域层（对应"模块职责混乱-问题一"）

**选择理由**：

这是最值得优先重构的问题，也是作为实验三切入点的最佳选择，原因如下：

1. **安全收益最高**：当前 6 条不变量中 3 条未实现、2 条实现在错误层次。这是系统中的"显性缺口"——需求文档明确规定了但代码没做到，评审时一眼就能发现。

2. **重构范围可控**：将 INV-01、INV-02、INV-03、INV-04、INV-05 集中到 `Task` 实体中，只需修改 `src/domain/Task.ts` 一个文件及其对应的领域层测试。不涉及应用层和接口层的改动，风险低、效果好。

3. **为后续重构清障**：不变量集中后，`DefaultTaskService.createTask` 中的校验逻辑可以简化为"委托给 Task"，该方法自然变短、职责变纯，同时缓解了"过长函数-问题一"和"模块职责混乱-问题二"。

4. **可测试性同步提升**：不变量集中到领域层后，可以用纯单元测试覆盖全部 6 条规则，不再需要 mock repository。

5. **修复成本远低于交付后修复**：领域不变量是业务规则，越晚修复破坏性越大。

**重构预期效果**：

| 指标 | 重构前 | 重构后预期 |
|------|--------|-----------|
| 领域层覆盖的不变量数 | 0 条 | 5-6 条 |
| 应用层的校验代码行数 | 约 25 行 | 约 5 行 |
| 不变量测试方式 | 需通过 Service 间接测试 | 可直接测试 Task 实体 |

---

## 第二优先级

### 抽取公共值解析逻辑（对应"重复代码-问题一"）

提取 `parsePriority` 和 `parseStatus` 中的公共模式——本质上都是"字符串→枚举"的泛型映射，可以提取为一个通用工具函数或装饰器。收益在于每新增一种枚举解析都不再需要复制粘贴，且解析行为可统一调整。

---

## 第三优先级

### 引入输出抽象解耦 Controller（对应"难以测试的耦合点-问题三"）

将 `TaskController` 中的 `console.log` 替换为一个可注入的 `OutputPort` 接口。该接口定义 `print(message: string)` 等方法，`ConsoleOutput` 实现输出到 stdout，`JsonOutput` 实现输出为 JSON。这个重构的收益主要在测试性上——Controller 层终于可以写单元测试了，但当前阶段若还没有引入 Web 框架，此重构的实际推动力有限。

---

## 不建议优先处理的问题

| 问题 | 不优先处理的原因 |
|------|----------------|
| `findAll()` 内存过滤重复（重复代码-问题二） | 当前数据量小，替换为数据库时才需改动。过早引入查询抽象会增加不必要的复杂度。 |
| Controller 空结果检查重复（重复代码-问题三） | 仅 2 处重复，影响范围小，修复成本与收益不成正比。 |
| 依赖注入容器（难以测试的耦合点-问题五） | 项目规模尚小，手动 DI 足够。引入 DI 容器（如 tsyringe）会增加工具链复杂度。 |

---

# 总结

从软件构造的可维护性角度看，本项目当前最大的问题不是代码"写错了"，而是**代码放错了位置**——领域规则写在应用层、展示逻辑写在控制器、时间依赖硬编码在实体中。

这种"职责错位"的问题在项目初期不会显露出危害，但随着功能的叠加（如图 2 所示），每一层都会变得越来越"脏"：领域层持续贫血、应用层持续臃肿、接口层难以替换。优先把领域不变量回归到领域层，就是以最小的改动成本为项目建立正确的架构锚点。
