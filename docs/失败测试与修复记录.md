## 记录一：状态转换边界不清导致的测试误判

### 关联提问

> "PENDING -> IN_PROGRESS 肯定可以，那 PENDING -> COMPLETED、COMPLETED -> PENDING、COMPLETED -> IN_PROGRESS 这些应该允许吗？"

### 问题描述

编写 `updateTaskStatus` 和 `completeTask` 的测试时，对状态转换规则的理解不够清晰，导致 TP011 和 TP015 的测试预期写反了。

**初始错误测试（TP011）：**

```typescript
it('TP011 PENDING 状态下直接 completeTask 应成功', () => {
  const task = createPending(service);
  // 错误预期：认为可以直接完成
  const done = service.completeTask(task.taskId);
  expect(done.status).toBe(TaskStatus.Completed);
});
```

**初始错误测试（TP015）：**

```typescript
it('TP015 PENDING → COMPLETED 应被允许', () => {
  const task = createPending(service);
  // 错误预期：认为是合法转换
  const updated = service.updateTaskStatus(task.taskId, 'COMPLETED');
  expect(updated.status).toBe(TaskStatus.Completed);
});
```

### 提问澄清

提问后发现需求文档 INV-04 明确规定状态只能沿单一方向流转（PENDING → IN_PROGRESS → COMPLETED），不允许跳步。同时也确认了 COMPLETED → PENDING 属于受控重置，需求允许。

### 修复方案

1. TP011 改为断言 `completeTask` 抛出"不允许的状态转换"
2. TP015 改为断言 `updateTaskStatus` 抛出"不允许的状态转换"
3. 新增 TP013（COMPLETED → PENDING 重置成功）和 TP016（COMPLETED → IN_PROGRESS 被拒绝）

### 涉及文件

| 文件 | 改动 |
|------|------|
| `test/application/TaskService.test.ts` | 修正 TP011、TP015 预期，新增 TP013、TP016 |
| `test/task.test.ts` | 修复集成测试中跳过 IN_PROGRESS 的问题 |

## 记录二："已完成可重置"与"已完成不能改回"的需求冲突

### 关联提问

> "之前需求里写的是'已完成任务不能改回未开始'，但是实际用的时候感觉重新开启任务也有道理。这种情况一般怎么设计比较合理？会不会影响后面的测试？"

### 问题描述

检测 `COMPLETED → PENDING` 重置路径时，发现领域建模中给出的不变量示例（"已完成任务不能再次被修改为未开始状态"）与需求文档 FR-04（"已完成的任务可重置为待开始"）相互矛盾。

测试 TP013 的初始实现按领域建模的不变量编写，断言重置被拒绝：

```typescript
it('TP013 COMPLETED → PENDING 应被拒绝', () => {
  const done = /* ... 先完成任务 */;
  // 按领域建模示例编写，错误预期重置被拒绝
  expect(() => service.updateTaskStatus(done.taskId, 'PENDING')).toThrow(
    '不允许的状态转换',
  );
});
```

同时，`DefaultTaskService.validateStatusTransition` 中也没有将 `COMPLETED → PENDING` 加入白名单。

### 提问澄清

提问后确认需求文档 FR-04 的优先级高于领域建模中的示例。已完成任务可重置为待开始，这一设计符合"学生想重新做一遍"的真实场景。

### 修复方案

1. `DefaultTaskService.validateStatusTransition` 补上 `COMPLETED → PENDING` 白名单
2. TP013 改为断言重置成功，且 `completedAt` 被清空
3. 提示词记录表中标记这条冲突的不变量已被删除

### 涉及文件

| 文件 | 改动 |
|------|------|
| `src/application/DefaultTaskService.ts` | `validateStatusTransition` 允许 `COMPLETED → PENDING` |
| `test/application/TaskService.test.ts` | TP013 改断言方向 |
| `docs/提示词记录表.md` | 标注领域建模人工修改中删除了冲突不变量 |

## 记录三：priority 类型设计不清晰导致测试层次错位

### 关联提问

> "priority 现在是 string。如果传个 'URGENT' 这种值系统也能收到。这里是继续用 string 判断比较好，还是直接改成枚举比较好？从测试角度看哪个更合理？"

### 问题描述

`CreateTaskCommand` 中 `priority` 定义为 `string`，导致服务层既要负责业务逻辑，又要负责字符串解析和校验。TP004 在 Service 测试中验证非法字符串，但按分层原则，这属于 Controller 层的测试职责。

**初始测试 TP004 的实现位置有误：**

```typescript
// 错误归属：在 Service 测试层测试 string 解析
it('TP004 priority 传入非法值时应抛出异常', () => {
  const { service } = createFixture();
  // 在 Service 层测 string 解析，不符合分层职责
  expect(() => service.createTask(cmd({ title: 'test', priority: 'URGENT' }))).toThrow(/无效优先级/);
});
```

同时，由于 `TaskController.handleCreateTask` 接受的是 `CreateTaskCommand`（含 string priority），Controller 层没有任何校验，非法值直接透传到了 Service 层才被发现。

### 提问澄清

提问后确认：`CreateTaskCommand` 是应用层 DTO，应该使用已经解析过的类型（`Priority` 枚举），字符串解析和校验应该控制在 Controller 层。

### 修复方案

1. `CreateTaskCommand.priority` 从 `string` 改为 `Priority` 枚举
2. `TaskController.handleCreateTask` 中新增 `string → Priority` 解析逻辑，非法值在 Controller 层报错返回
3. Service 层 `createTask` 去掉 `parsePriority` 调用，直接使用传入的枚举值
4. TP004 从 Service 测试移至 Controller 测试，改为测试 `handleCreateTask` 传入 `"URGENT"` 时的行为

### 涉及文件

| 文件 | 改动 |
|------|------|
| `src/application/TaskService.ts` | `CreateTaskCommand.priority` 类型改为 `Priority` |
| `src/interfaces/TaskController.ts` | 新增 string→Priority 解析，非法值早返回 |
| `src/application/DefaultTaskService.ts` | `createTask` 去掉 `parsePriority` |
| `test/application/TaskService.test.ts` | 删除 TP004（移至 Controller 测试） |
| `test/interfaces/TaskController.test.ts` | 新增 Controller 层测试（TP004 迁移至此） |
| `docs/接口契约说明.md` | 同步更新参数类型说明 |
